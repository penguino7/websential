1. MỤC ĐÍCH DỰ ÁN
=================

Đây là một công cụ kiểm thử bảo mật web dạng crawler + fuzzer + analyzer.

Mục tiêu chính:
- Crawl website trong phạm vi cấu hình để phát hiện endpoint có query/form/API.
- Phân loại rủi ro endpoint bằng LLM Ollama hoặc rule-based fallback.
- Sinh payload kiểm thử SQL Injection và XSS.
- Fuzz endpoint bằng HTTP request, có một phần xác nhận XSS bằng Playwright.
- Phân tích log thành finding bảo mật có OWASP/CWE/CVSS, dùng AI và rule cross-check.

Luồng xử lý tổng thể:
1. tests/run_all.py tạo thư mục session theo config.SESSION_ID.
2. crawler.crawler.crawl() gọi static crawler và tùy chọn JS crawler.
3. crawler.classifier.classify() gán risk_level và likely_vulns cho endpoint.
4. fuzzer.payload_planner.generate_plan() tạo payload plan dựa trên likely_vulns.
5. fuzzer.sqli_fuzzer.fuzz_sqli() kiểm thử SQLi nhiều kỹ thuật.
6. fuzzer.xss_fuzzer.fuzz_xss() kiểm thử reflected XSS và xác nhận bằng Playwright.
7. tests/run_all.py ghi logs.jsonl.
8. analyzer.log_analyzer.analyze() đọc logs.jsonl và ghi findings.json.


2. KIẾN TRÚC TỔNG QUAN
======================

Điểm tốt:
- Project được chia module khá rõ: crawler, fuzzer, analyzer, llm, tests.
- Dữ liệu trung tâm có dataclass Endpoint và LogEntry, giúp truyền dữ liệu giữa các module nhất quán hơn.
- Có fallback rule-based khi Ollama lỗi/offline.
- Có static crawler và dynamic crawler bằng Playwright, phù hợp cho cả site HTML truyền thống và SPA.
- Có phân tách SQLi fuzzer và XSS fuzzer chuyên biệt, tốt hơn generic fuzzer.
- Có cơ chế cross-check trong analyzer để giảm hallucination từ AI.

Điểm yếu chính:
- tests/run_all.py hiện đặt DRY_RUN=True nhưng lại bỏ qua generate_plan(), làm payload plan rỗng. Kết quả là SQLi/XSS fuzzer gần như không chạy request nào.
- fuzzer/fuzzer.py bị lệch interface và thiếu tham số technique khi tạo LogEntry, nếu dùng generic fuzz() sẽ lỗi runtime.
- Classifier rule-based hiện bỏ sót nhiều param có khả năng XSS như tfSearch, RetURL; một số endpoint được đánh high nhưng likely_vulns rỗng nên fuzzer không kiểm thử.
- analyzer.analyze() không ghi findings.json rỗng khi không có log vulnerable, dễ giữ lại findings.json cũ và gây hiểu nhầm.
- sessions/*.json và __pycache__ đang được track trong git; đây là dữ liệu runtime/generated, không nên là source chính.
- Không có requirements.txt/pyproject.toml nên khó tái tạo môi trường.
- Không có unit test thật; tests/run_all.py là integration runner có side effect mạng.


3. LUỒNG HOẠT ĐỘNG CHI TIẾT THEO PIPELINE
=========================================

3.1. Cấu hình
-------------

- OLLAMA_MODEL = qwen2.5-coder:14b
- TARGET_URL = http://testasp.vulnweb.com/

- SESSION_ID = testasp_01

Project hiện phụ thuộc mạnh vào file config.py, chưa có CLI/env var để đổi target/session an toàn.

3.2. Crawl
----------
crawler.crawler.crawl(session_dir, use_ai=True):
- Tạo session_dir.
- Gọi static_crawl(TARGET_URL, SCOPE, MAX_DEPTH, CRAWL_DELAY).
- Nếu USE_JS=True thì import js_crawl() và merge endpoint static + JS.
- Gọi classify(endpoints, use_ai).
- Bỏ endpoint risk_level=skip.
- Sort high -> medium -> low.
- Cắt theo MAX_ENDPOINTS.
- Ghi endpoints.json.

static_crawl():
- BFS từ target_url.
- Seed thêm path từ robots.txt và sitemap.xml.
- Bỏ URL ngoài scope hoặc file tĩnh.
- GET từng page.
- Thu endpoint từ query string URL hiện tại và link <a href>.
- Parse form thành endpoint POST/GET với params từ input/textarea/select.
- Tìm URL ẩn trong script inline và file JS bằng regex.

js_crawl():
- Dùng Playwright Chromium headless.
- Hook event request để bắt xhr/fetch/document.
- Load target, collect link/form sau render.
- Scroll page để kích hoạt lazy-load.
- Auto-click các selector phổ biến như nav a, button, role=tab, menu item.
- Bỏ qua text/href chứa logout, delete, remove.

3.3. Phân loại rủi ro
---------------------
crawler.classifier.classify():
- Nếu use_ai=False: dùng _rule_classify().
- Nếu use_ai=True: chia batch 5 endpoint, gửi prompt qua llm.ollama_client.call_json().
- Nếu AI lỗi hoặc output không phải list: fallback rule-based cho batch.

Rule-based:
- integer param -> high, likely_vulns gồm sqli + idor.
- path admin/user/account/order/api/auth/login/register/profile -> high.
- param id/user_id/file/path/token/redirect -> high.
- param q/query/search/name/msg/comment -> xss, medium nếu chưa high.
- không có param -> skip.

3.4. Payload planning
---------------------
fuzzer.payload_planner.generate_plan():
- Kiểm tra Ollama bằng is_alive().
- Chỉ lấy endpoint risk_level high/medium.
- Nếu endpoint likely_vulns có sqli: detect backend mssql/mysql/generic rồi chọn payload SQLi.
- Nếu likely_vulns có xss: detect context html_body/html_attribute/js_context rồi chọn payload XSS.
- Nếu AI offline thì vẫn fallback payload generic.

refine_plan():
- Dùng ở vòng adaptive.
- Lọc log có signal như status khác baseline, status 400/500, snippet chứa error/syntax/blocked/encoded.
- Gửi signal logs cho AI sinh payload mới.
- Dừng nếu Ollama offline hoặc không có signal.

3.5. Fuzz SQLi
--------------
fuzzer.sqli_fuzzer.fuzz_sqli():
- Lọc endpoints có "sqli" trong likely_vulns.
- Lấy baseline request.
- Vòng 1: chạy payload từ plan theo kỹ thuật error, time, boolean, union.
- Vòng 2..MAX_ROUNDS: nếu chưa có high confidence thì gọi refine_plan() để lấy payload mới.
- Ghi LogEntry cho mỗi request.

Phát hiện:
- error_based/union_based: tìm SQL error signature hoặc status 500 khi baseline 200.
- time_based: duration > 3500ms.
- boolean_based: response TRUE/FALSE khác nhau > 100 bytes và status đều 200.

3.6. Fuzz XSS
-------------
fuzzer.xss_fuzzer.fuzz_xss():
- Lọc endpoints có "xss" trong likely_vulns.
- Với từng param: probe reflection bằng PROBE_TEXT.
- Nếu có reflection, chạy payload XSS qua HTTP.
- Payload reflect nguyên văn -> suspect medium.
- Payload HTML-encoded -> suspect low.
- Candidate suspect sẽ được mở bằng Playwright để xem alert() có trigger thật không.
- Nếu Playwright confirm, set confidence=high và playwright_confirmed=True.

3.7. Analyze
------------
analyzer.log_analyzer.analyze(session_dir):
- Đọc logs.jsonl.
- Lọc log có is_vulnerable=True.
- Log XSS đã playwright_confirmed được tạo Finding High ngay.
- Log còn lại gửi AI phân tích theo batch 5.
- Nếu AI lỗi thì fallback _rule_analyze().
- _cross_check() hạ một số finding High xuống Medium nếu thiếu bằng chứng.
- Ghi findings.json.

4.13. fuzzer/sqli_fuzzer.py
---------------------------
Mục đích:
- Kiểm thử SQL Injection chuyên biệt với multi-round adaptive fuzzing.

Luồng hoạt động:
- fuzz_sqli() lọc endpoint có likely_vulns chứa sqli.
- Với từng endpoint: baseline, vòng 1 payload plan, các vòng refine bằng AI.
- _fuzz_one_round() chạy error/time/boolean/union payload.
- _send() gửi request và detect.

Đánh giá:

- req_count chỉ tính LogEntry, boolean-based thực tế gửi 2 request nhưng tính 1.
- time_based dùng ngưỡng tuyệt đối 3500ms, không so với baseline duration; dễ false positive trên endpoint chậm.
- Không hỗ trợ cookie/auth mặc dù Endpoint có requires_auth.

4.14. fuzzer/xss_fuzzer.py
--------------------------
Mục đích:
- Kiểm thử reflected XSS bằng HTTP fuzz và xác nhận alert() bằng Playwright.

Luồng hoạt động:
- fuzz_xss() lọc endpoint có likely_vulns chứa xss.
- _check_reflection() probe từng param.
- _fuzz_http() gửi payload và detect reflection.
- _detect_http() check payload raw hoặc encoded trong body.
- _playwright_confirm() mở browser và test candidate payloads.
- _build_form_js() điền form POST bằng JS rồi submit.

Đánh giá:
- Có bước Playwright confirmation là điểm mạnh, giảm false positive.
- Lỗi logic: candidates chỉ lưu payload, không lưu param; _playwright_confirm() luôn inject vào ep.params[0]. Endpoint nhiều param có thể confirm sai param hoặc bỏ sót vuln.
- used_payloads dùng chung cho endpoint, không gồm param; có thể bỏ qua test cùng payload ở param khác.
- _detect_http() đánh is_vulnerable=True cho HTML-encoded payload; analyzer có thể biến thành finding dù chưa executable.
- _build_form_js() escape còn tối thiểu; payload chứa backslash hoặc pattern JS phức tạp có thể làm script evaluate lỗi.

- Có RAG/prompt nội bộ và cross-check là hướng tốt.
- Nếu logs.jsonl không tồn tại, rỗng hoặc không có vuln logs, analyze() return [] nhưng không ghi findings.json rỗng. Điều này có thể để lại findings cũ trong session.
- _rule_analyze() tạo finding Medium cho mọi log is_vulnerable, phụ thuộc hoàn toàn vào fuzzer; nếu fuzzer low-confidence false positive thì analyzer vẫn giữ.
- _cross_check() chủ yếu hạ High, chưa loại Medium false positive.
- _load_logs() chưa handle JSONL lỗi từng dòng; một dòng hỏng sẽ làm analyze fail.

5. CÁC VẤN ĐỀ ƯU TIÊN
====================

Mức Critical/High:
1. tests/run_all.py DRY_RUN không fuzz thật
   - File: tests/run_all.py, dòng 22 và 52.
   - DRY_RUN=True set ai_payloads = {}.
   - fuzz_sqli/fuzz_xss yêu cầu plan có ep.id nên sẽ skip target.
   - Cách sửa: luôn gọi generate_plan(endpoints); để generate_plan tự fallback khi Ollama offline, hoặc tạo generate_static_plan().

2. Generic fuzzer bị lỗi runtime
   - File: fuzzer/fuzzer.py, _send().
   - LogEntry bắt buộc có technique nhưng _send() không truyền.
   - fuzzer/__init__.py vẫn export fuzz, dễ gọi nhầm.
   - Cách sửa: truyền technique theo vuln_type hoặc bỏ generic fuzzer.

3. Analyzer có thể giữ findings cũ
   - File: analyzer/log_analyzer.py, analyze().
   - Khi không có log hoặc không có vulnerable log, hàm return [] mà không ghi findings.json rỗng.
   - sessions/testasp_01 hiện có logs.jsonl rỗng nhưng findings.json vẫn có dữ liệu.
   - Cách sửa: luôn _save([], session_dir) trước khi return trong các nhánh empty.

4. Scope check chưa an toàn
   - File: crawler/utils.py, in_scope().
   - re.search(scope, netloc) không escape domain và có thể match sai host.
   - Cách sửa: parse hostname lower, so sánh exact/subdomain.

Mức Medium:
5. Classifier bỏ sót XSS param
   - File: crawler/classifier.py.
   - tfSearch không match MED_PARAMS nên Search.asp bị low/no vuln.
   - Cách sửa: normalize param name tốt hơn, thêm contains rule cho search/query/q/comment/msg/name, hoặc map theo input type/source form.

6. Endpoint high nhưng không có likely_vulns
   - File: crawler/classifier.py.
   - Path login/register làm high nhưng Register.asp có likely_vulns rỗng.
   - Fuzzer chỉ chạy theo likely_vulns nên endpoint high không được test.
   - Cách sửa: nếu high do login/auth thì gán auth_bypass; nếu form text thì cân nhắc xss/sqli theo param.

7. Multi-param fuzzing bị bỏ sót
   - File: fuzzer/sqli_fuzzer.py và fuzzer/xss_fuzzer.py.
   - used_payloads không include param, nên payload dùng cho param đầu không được thử lại ở param sau.
   - XSS Playwright confirm cũng không giữ param, chỉ inject ep.params[0].
   - Cách sửa: key used theo (param, payload), candidates lưu (param, payload).

8. Time-based SQLi dễ false positive
   - File: fuzzer/sqli_fuzzer.py.
   - Dùng ngưỡng tuyệt đối 3500ms, không so baseline duration.
   - Cách sửa: lưu baseline duration và yêu cầu delta đủ lớn, chạy confirm lại 2 lần.

9. Thiếu dependency manifest
   - Project import requests, bs4, playwright nhưng không có requirements.txt/pyproject.
   - Cách sửa: thêm requirements.txt hoặc pyproject.toml, kèm hướng dẫn playwright install.

10. Runtime/generated files đang được track
   - __pycache__ và sessions output nằm trong git.
   - Cách sửa: thêm .gitignore, bỏ track pycache/session generated nếu không cần fixture.

Mức Low:
11. Nhiều except Exception: pass làm khó debug
   - File: crawler/static_crawler.py, crawler/js_crawler.py.
   - Nên log debug có ngữ cảnh.

12. LLM JSON parse chưa chặt
   - File: llm/ollama_client.py.
   - Regex greedy có thể parse sai nếu output lẫn text.
   - Nên yêu cầu format JSON và validate schema ở caller.

13. tests folder không chứa test thật
   - tests/run_all.py là runner.

7. KẾT LUẬN
===========

Project có ý tưởng và module hóa tốt cho một scanner/fuzzer bảo mật web dùng cả rule-based và LLM. Kiến trúc tổng thể dễ hiểu: crawl endpoint -> classify risk -> plan payload -> fuzz SQLi/XSS -> analyze finding.

Tuy nhiên trạng thái hiện tại có vài lỗi logic khiến pipeline dễ không tạo kết quả đúng, đặc biệt DRY_RUN tạo plan rỗng, generic fuzzer lỗi LogEntry, analyzer có thể giữ findings cũ, và classifier bỏ sót candidate XSS. Nếu sửa các điểm ưu tiên trên, codebase sẽ ổn hơn đáng kể về tính đúng đắn, khả năng tái chạy và độ tin cậy khi báo cáo lỗ hổng.
